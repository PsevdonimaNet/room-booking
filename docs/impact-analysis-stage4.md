# Impact analysis: этап 4

## 1. Изменения

| # | Тип | Описание |
|---|---|---|
| 1 | Модификация | VIP-комнаты: бронирование требует подтверждения администратором (статусы `pending`, `rejected`) |
| 2 | Новая функция | Экспорт бронирований в CSV с фильтрами по дате, комнате и статусу; страница отчёта со сводкой |
| 3 | Новая функция | Уведомления: двойное бронирование, новая заявка на VIP, решение администратора |

## 3. Что не затронуто

Авторизация и роли, модель `Booking` (поля и ограничение `end > start`), правила длительности и рабочего времени, health-check, CI/CD, Docker.

## 4. Обратная совместимость

- Существующие брони остаются `confirmed`, API создания и отмены не изменился.
- Новые поля в ответах API (`is_vip`, новые значения `status`) добавлены без удаления старых.

## 5. Тесты

**Существующие тесты** (`bookings/tests.py`, `web/tests.py`) не менялись и должны проходить без правок: это регрессионная проверка того, что обычные комнаты работают как раньше.

**Новые тесты:**
- `bookings/tests_stage4.py`: VIP-поток (создание, подтверждение, отклонение, права), блокировка слота ожидающей бронью, отмена новых статусов, уведомления (в том числе их сохранность при ошибке конфликта), фильтры и сводка отчёта, CSV и его защита от инъекций, API `approve/reject/export`.
- `web/tests_stage4.py`: страницы заявок, уведомлений, отчёта, скачивание CSV, права доступа.

## 6. Принятые решения

- **Ожидающая бронь занимает слот.** Иначе подтверждение могло бы привести к двойному бронированию.
- **Уведомления создаются вне транзакции.** Иначе они откатывались бы вместе с ошибкой конфликта.
- **Экспорт и отчёты только для администратора:** в отчёте видны данные всех пользователей.
