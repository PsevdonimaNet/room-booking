## Подробные описания

### D-001. Нагрузочный тест получал 403
- **Шаги:** запустить k6 со сценарием входа в каждой итерации (cookies сбрасываются).
- **Ожидалось:** запросы выполняются от имени пользователя (200).
- **Фактически:** 26 052 ответа 403 (`user=anonymous`), 668 ответов 200; p95 4 мс (запросы отклонялись до работы с БД).
- **Причина:** k6 по умолчанию сбрасывает cookies на каждой итерации.
- **Исправление:** опция `noCookiesReset`; позже вход вынесен в `setup()`. **Регрессия:** повторные прогоны 50/100/200 запр./с дали 100% успешных проверок.

### D-002. Массовый вход искажает измерения
- **Шаги:** k6, 100 и 200 запр./с, вход в каждом виртуальном пользователе.
- **Фактически:** p95 554 мс и 1.85 с при медиане 7 мс; число виртуальных пользователей росло до 500, пропущено до 1925 итераций.
- **Причина:** хэширование пароля (p95 входа около 0.5 с) занимает процессор, обычные запросы ждут. Число ответов 302 совпадало с числом виртуальных пользователей.
- **Исправление:** вход один раз на пользователя в `setup()`. **Результат:** p95 12.9 мс (100 запр./с), 18.5 мс (200 запр./с). Свойство системы (вход ресурсоёмок) описано в рисках (R-3).

### D-003. `/health/` отвечает 500 при недоступной БД
- **Шаги:** войти в браузере, выполнить `docker compose stop db`, открыть `/health/`.
- **Ожидалось:** 503 и JSON `degraded`. **Фактически:** `Server Error (500)`, 8 с.
- **Причина:** middleware журналирования запрашивал имя пользователя из БД после ответа.
- **Исправление:** журналирование не обращается к БД, если она недоступна. **Регрессия:** `/health/` 503 `degraded` за около 4 с, после запуска БД 200; добавлены автотесты.

### D-004. Зависание запросов при недоступной БД
- **Шаги:** нагрузка 150 запр./с, остановить БД на 2.5 минуты.
- **Фактически:** `request timeout`, p95 36 с, 21 246 пропущенных итераций, в метриках нет ответов 5xx (завершённых ответов не было), сработал только `ServiceDown`.
- **Причина:** каждый запрос ждал подключения, потоки сервера блокировались.
- **Исправление:** таймаут подключения 2 с, быстрый отказ 503 (`core/db_guard.py`), ответы 503 попадают в метрики. **Регрессия:** повторный тест: p95 API 21 мс, сработали `DatabaseDown`, `AvailabilityBelowSLA`, `HighErrorRate`, восстановление без перезапуска.

### D-005. Сборка образа в CI: заглавные буквы
- **Фактически:** `invalid tag "ghcr.io/PsevdonimaNet/room-booking:latest": repository name must be lowercase`.
- **Исправление:** имя образа приводится к нижнему регистру в workflow. Регрессия: CI зелёный, образ опубликован.

### D-006. Деплой на Render
- **Фактически:** `Exited with status 127`, в журнале `not found` для всей строки запуска.
- **Исправление:** команды запуска перенесены в скрипт `start.sh`. Регрессия: сайт на Render открывается.

### D-007. Затёртый файл CI
- **Причина:** архив с обновлением содержал старую версию `ci.yml`. **Исправление:** файл возвращён; обновления выдаются только изменёнными файлами. Регрессия: CI зелёный.

### D-008. Русский текст в JSON ответа 503
- **Фактически:** `"\u0421\u0435\u0440..."` в браузере (клиенты API корректно разбирают такой JSON).
- **Предлагаемое исправление:** `json_dumps_params={"ensure_ascii": False}` в `core/db_guard.py`.

### D-009. Уязвимости зависимостей
- **Фактически:** `pip-audit`: Django 5.1.15 (9 записей, исправления в 5.2.15-5.2.17), DRF 3.15.2 (5 записей, исправления в 3.17.2 и 3.18.2).
- **Решение:** на период практики риск принят (стенд с тестовыми данными). **Рекомендация:** обновить до Django 5.2 LTS и DRF 3.18, затем повторить тесты, `makemigrations --check` и `pip-audit`.

### D-010 - D-014. Улучшения
- **D-010:** добавить пагинацию (`PageNumberPagination`) для списков.
- **D-011:** закрыть `/metrics` на уровне Nginx или сети.
- **D-012:** загружать профиль и роль вместе с пользователем (`select_related`), кэшировать роль.
- **D-013, D-014:** особенности окон правил алертов (5 минут) и проверки доступности БД; допустимы для MVP.
