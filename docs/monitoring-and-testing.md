# Мониторинг, надёжность и тестирование

## 1. SLA и показатели (SLI)

| Показатель | Цель (SLO) | Как измеряется | Алерт |
|---|---|---|---|
| Доступность | >= 99.9% | доля ответов без 5xx за 5 мин; метрика `up` | `AvailabilityBelowSLA`, `ServiceDown` |
| Время ответа | p95 <= 200 мс | гистограмма `django_http_requests_latency_seconds_by_view_method` | `HighLatencyP95` |
| Доля ошибок | <= 0.1% | ответы 5xx / все ответы | `HighErrorRate` |
| База данных | доступна, соединений < 80% лимита | `pg_up`, `pg_stat_activity_count` | `DatabaseDown`, `DatabaseConnectionsHigh` |

Допустимый простой при 99.9%: около 43 минут в месяц (0.1% от 30 суток).

## 2. Что собирается

| Группа | Метрики | Источник |
|---|---|---|
| HTTP-запросы | число, методы, статусы, время ответа по представлениям | django-prometheus (`/metrics`) |
| Ошибки | ответы 5xx, ошибки БД `django_db_errors_total` | django-prometheus |
| Соединения с БД | `pg_stat_activity_count`, `pg_settings_max_connections`, новые соединения | postgres-exporter, django-prometheus |
| Запросы к БД | `django_db_execute_total` | django-prometheus |
| Очереди | не применимо: в MVP нет фоновых очередей (уведомления создаются синхронно) | - |

Логи: `logs/app.log` и консоль контейнера (действия пользователей, конфликты, ошибки, каждый HTTP-запрос с временем ответа).

## 3. Запуск мониторинга

```powershell
# в .env: DJANGO_DEBUG=0 (для замеров производительности)
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up --build -d
docker compose exec web python manage.py seed_demo --load-users 20
```

| Сервис | Адрес |
|---|---|
| Приложение | http://localhost:8000 |
| Метрики приложения | http://localhost:8000/metrics |
| Prometheus (запросы, алерты в разделе Alerts) | http://localhost:9090 |
| Grafana (дашборд «Бронирование: SLA и надёжность») | http://localhost:3000 (admin / admin) |

Демо-данные: пользователи `ivan`, `maria`, `petr` и администратор `manager`, пароль `demo12345`.

## 4. Стресс-тест (k6)

Сценарий: рост нагрузки 50 -> 100 -> 200 запросов/с (3.5 мин). Состав запросов: 65% список комнат, 15% занятость, 12% история, 8% создание брони (часть вернёт 409/400, это ожидаемо).

```powershell
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml --profile load run --rm k6
```

Критерии (thresholds в скрипте): p95 < 200 мс, доля ошибок < 0.1%. Итог сохраняется в `loadtests/results/summary.json`. Во время теста держите открытым дашборд Grafana.

### Деградация БД

Во время теста (на отметке 200 запросов/с) в другом терминале:

```powershell
docker compose stop db      # имитация отказа БД
# подождать 30-40 секунд, наблюдать дашборд и Prometheus -> Alerts
docker compose start db     # восстановление
```

Ожидаемое поведение: приложение быстро (без зависаний) отвечает 503 на запросы, `/health/` показывает `degraded`, растёт доля 5xx, срабатывают алерты `DatabaseDown`, `HighErrorRate`, `AvailabilityBelowSLA`; после запуска БД приложение восстанавливается без перезапуска.

Наблюдение первого прогона (до доработки): запросы не получали 503, а зависали на таймауте, потому что при недоступной БД каждый запрос ждал подключения; потоки gunicorn были заняты, приложение переставало отвечать даже на `/metrics`, а метрики ответов не показывали сбой (завершённых ответов 5xx не было). Сработал только алерт `ServiceDown`. Доработка: короткий `connect_timeout` (2 с), быстрый отказ 503 после первой ошибки (`core/db_guard.py`) и отдельный контроль по метрике `up`.

## 5. Статический анализ и качество кода

| Инструмент | Что проверяет | Где запускается |
|---|---|---|
| ruff (линтер и форматтер) | стиль, ошибки, порядок импортов | CI, задача `lint` |
| bandit | уязвимости в коде (небезопасные вызовы, секреты) | CI, `security.yml` |
| pip-audit | известные уязвимости в зависимостях | CI, `security.yml` |
| ruff с правилами S, C90, SIM, DJ | сложность, запахи кода, ошибки Django | CI, справочно |
| `makemigrations --check` | согласованность моделей и миграций | CI, задача `test` |
| coverage | покрытие тестами (порог 70%) | CI, задача `test` |

Локально: `pip install bandit pip-audit`, затем `bandit -r bookings core config web -x "*/tests*.py" -ll` и `pip-audit -r requirements.txt`.

## 6. Ограничения MVP (для раздела «что улучшить»)

- Нет Alertmanager: алерты видны в Prometheus и Grafana, но не отправляются в почту или мессенджер.
- `/metrics` открыт: в продакшене его нужно закрыть на уровне reverse proxy (Nginx) или сети.
- Одна реплика приложения и БД: отказоустойчивость требует репликации PostgreSQL и нескольких экземпляров приложения за балансировщиком.
- Нагрузочные тесты запускаются на одной машине вместе с приложением, поэтому абсолютные цифры ориентировочные.
