# Техническое задание (краткое)

## 1. Цель и назначение

Веб-приложение для бронирования переговорных комнат в офисе: сотрудники просматривают комнаты и их занятость, бронируют на 1-4 часа; администратор управляет комнатами, ролями и подтверждает брони VIP-комнат. Цель практики: реализовать MVP и подготовить его к опытной эксплуатации.

## 2. Пользователи и роли

| Роль | Возможности |
|---|---|
| Пользователь | вход и регистрация, просмотр комнат и занятости, бронирование, отмена своих броней, история, уведомления |
| Администратор | всё перечисленное + CRUD комнат, назначение ролей, подтверждение/отклонение заявок на VIP-комнаты, просмотр всех броней, отчёты и экспорт CSV, Django-админка (суперпользователь) |

## 3. Функциональные требования

| ID | Требование | Реализация |
|---|---|---|
| FR-1 | Авторизация: вход, выход, регистрация | `/accounts/login/`, `/accounts/signup/`; API: сессия или Basic |
| FR-2 | Просмотр списка переговорных | `/rooms/`, `GET /api/rooms/` |
| FR-3 | Занятость комнаты по часам на выбранную дату | страница комнаты, `GET /api/rooms/{id}/availability/` |
| FR-4 | Бронирование на 1-4 часа (целые часы, рабочее время 08:00-20:00, не в прошлом) | `bookings/services.py::validate_interval` |
| FR-5 | Отмена бронирования (владелец или администратор) | `POST /api/bookings/{id}/cancel/`, кнопка в истории |
| FR-6 | История бронирований (своя; у администратора общая) | `/bookings/`, `GET /api/bookings/` |
| FR-7 | Защита от двойного бронирования, понятная ошибка конфликта | блокировка строки комнаты + проверка пересечений; ответ 409 `booking_conflict` |
| FR-8 | Администратор: добавление, изменение, отключение комнат | `/manage/rooms/`, `/api/rooms/` (удаление = отключение) |
| FR-9 | Администратор: управление ролями пользователей | `/manage/users/` |
| FR-10 | VIP-комнаты: бронь ожидает подтверждения администратором | статусы `pending`/`confirmed`/`rejected`, `/manage/pending/` |
| FR-11 | Отчётность: сводка по комнатам, экспорт в CSV с фильтрами (дата, комната, статус) | `/manage/report/`, `GET /api/bookings/export/` |
| FR-12 | Уведомления: конфликт бронирования, заявка на VIP, решение администратора | `/notifications/`, счётчик в меню |
| FR-13 | Логирование действий пользователей и ошибок | `logs/app.log`, консоль контейнера; каждый HTTP-запрос с пользователем и временем |

## 4. Нефункциональные требования

| ID | Требование | Как проверяется |
|---|---|---|
| NFR-1 | Время отклика API p95 <= 200 мс | нагрузочный тест k6 (`loadtests/booking.js`), дашборд Grafana |
| NFR-2 | Доступность >= 99.9% | метрики и алерты Prometheus; быстрый отказ 503 при сбое БД |
| NFR-3 | Доля ошибок 5xx <= 0.1% | алерт `HighErrorRate` |
| NFR-4 | Покрытие автотестами >= 70% критических модулей | `coverage report` в CI (порог 70%) |
| NFR-5 | Безопасность: роли, CSRF, хэширование паролей, защита CSV от инъекций, анализ кода и зависимостей | тесты прав доступа, bandit, pip-audit |
| NFR-6 | Переносимость: запуск одной командой | Docker Compose |
| NFR-7 | Сопровождаемость: единый стиль, CI на каждый push | ruff, GitHub Actions |
| NFR-8 | Документация API в формате OpenAPI | `/api/schema/`, `/api/docs/` |

## 5. Ограничения и допущения

- Часовой пояс системы задаётся настройкой `TIME_ZONE` (по умолчанию Europe/Moscow).
- Рабочее время бронирования и длительность задаются настройками `BOOKING_*` в `config/settings.py`.
- Уведомления внутри системы; почтовые и push-уведомления не входят в MVP.
- Нагрузочные цифры получены на одной машине (разработческий стенд), поэтому ориентировочные.

## 6. Вне рамок MVP

Интеграция с календарями (Outlook, Google), SSO, мобильное приложение, повторяющиеся брони, почтовые уведомления.

## 7. Критерии приёмки

1. Все требования FR-1 - FR-13 проверены чек-листом (`07-pilot-testing.md`), критические сценарии пройдены.
2. Автотесты проходят, покрытие не ниже 70%.
3. При нагрузке 100 запросов/с p95 <= 200 мс и ошибок API нет.
4. Отказ БД не приводит к зависанию: сервис отвечает 503, алерты срабатывают, после восстановления работа возобновляется без перезапуска.
5. Документация комплектна, дефекты занесены в реестр, критические и высокие исправлены или обоснованно приняты.
