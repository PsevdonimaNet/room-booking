## 3. Результаты измерений

Состав запросов: 65% список комнат, 15% занятость, 12% история, 8% создание брони (часть конфликтов 409/400). Вход выполнялся один раз на пользователя.

| Нагрузка, запр./с | CPU web, % ядра | CPU БД, % ядра | CPU Redis, % ядра | p95 API | Ошибки API |
|---|---|---|---|---|---|
| 50 | 27 | 5 | 3.7 | 11.6 мс | 0 |
| 100 | 51 | 13 | 1.4 | 12.9 мс | 0 |
| 200 | 120 | 21 | 2.4 | 18.5 мс | 0 |
| 400 | 349 | 54 | 4.7 | 89 мс | 0 |
| 600 | 517 | 64 | 5.1 | 1.4 с (насыщение) | 0 |

Другие измерения: память контейнера web (4 процесса) около 270 МБ, БД около 65 МБ, Redis около 7 МБ; ответ API в среднем около 2 КБ; число соединений с БД на нагрузке до 15 из 100.

Выводы: система держит около 400 запр./с при p95 < 200 мс; предел около 390 запр./с, узкое место процессор процессов web (Python). Вход в систему ресурсоёмок (p95 около 0.5 с, хэширование пароля) и при массовом входе замедляет остальные запросы.

## 4. Расчёт ресурсов для 1000 одновременных пользователей и 100 запр./с

**Допущения.** 1000 пользователей, каждый в среднем делает один запрос раз в 10 секунд: 1000 / 10 = 100 запр./с. Пик принимаем равным 2 x 100 = 200 запр./с. Целевая загрузка процессора не более 60%. Облачное ядро (vCPU) медленнее ядра настольного процессора, берём коэффициент 1.5 (допущение, проверяется нагрузочным тестом на целевой среде).

**Процессор приложения.** На 200 запр./с измерено 1.2 ядра. С учётом облачного коэффициента: 1.2 x 1.5 = 1.8 ядра; при загрузке 60%: 1.8 / 0.6 = 3 vCPU. Для отказоустойчивости берём два узла по 2 vCPU (всего 4 vCPU, при потере одного узла остаётся 2 vCPU, достаточно для штатных 100 запр./с).

**Процессор БД.** На 200 запр./с измерено 0.21 ядра: 0.21 x 1.5 / 0.6 = 0.53 vCPU. Выбираем 2 vCPU (запас на отчёты, репликацию, резервное копирование).

**Память.** Приложение: около 0.3 ГБ на узел плюс ОС и Nginx, достаточно 2-4 ГБ. БД: данные малы, кэш PostgreSQL `shared_buffers` около 25% памяти, берём 4 ГБ. Redis: сессии 1000 пользователей занимают порядка мегабайта, 1 ГБ с запасом.

**Диск.** Данные: 1000 сотрудников, около одной брони в неделю, около 50 тыс. броней в год, строка с индексами около 0.5 КБ: порядка 25 МБ в год, с уведомлениями и журналами БД не более 1-2 ГБ в год. Журналы приложения: в среднем 20 запр./с x 36 000 с x 110 Б около 80 МБ в сутки, при хранении 30 дней около 2.4 ГБ. Метрики Prometheus при хранении 15 дней около нескольких ГБ. Резервные копии: 7 суточных копий. Итого: SSD 40 ГБ для узла приложения, 100 ГБ для БД, 50 ГБ для мониторинга.

**Сеть.** 100 запр./с x 2 КБ = 200 КБ/с около 1.6 Мбит/с, достаточно канала 100 Мбит/с, берём 1 Гбит/с внутри ЦОД.

**Соединения с БД.** 2 узла x 4 процесса x 4 потока = 32 соединения, лимит 100 (по умолчанию) достаточен.

## 6. Отказоустойчивость

| Мера | Реализация |
|---|---|
| Проверка здоровья | `/health/` (БД и Redis), healthcheck контейнера, метрика `up` |
| Автоперезапуск | `restart: unless-stopped` в Docker Compose |
| Быстрый отказ при сбое БД | `core/db_guard.py`: ответ 503 вместо зависания; таймаут подключения 2 с |
| Резервирование приложения | два узла за Nginx |
| Репликация БД | потоковая репликация PostgreSQL (в MVP не развёрнута) |
| Резервные копии | суточный `pg_dump` + хранение 7 копий, проверка восстановления (см. руководство администратора) |
| Мониторинг и алерты | Prometheus: недоступность, ошибки, задержка, соединения с БД |

Допустимый простой при доступности 99.9%: 0.001 x 43 200 мин = 43.2 мин в месяц. В тесте с отказом БД на 2.5 минуты израсходовано около 6% этого бюджета.
